Multi-agent milestone workflow

Setting up a new project so that several AI agents work through the tasks of a milestone on their own, and the maintainer reviews only the finished milestone before it reaches main.

1. The idea

In a classic feature-branch workflow with manual review, every single task waits for the maintainer. Here the human gate moves up one level: tasks are implemented, reviewed and merged by agents into a milestone branch, and only the whole milestone gets a full test run, a full review and the maintainer's manual review before it is merged into main.

  • main stays the base for everything; nothing reaches it without the maintainer's approval.
  • Work is planned in milestones, tasks and sub-tasks (Backlog.md, managed with backlog-ng).
  • Per task: the minimal test suite (fast tests). Per milestone: the full test suite including end-to-end tests. A regression becomes a fix task before the manual review.
  • Reviews look only at new and changed code, report only real findings, and stop after a fixed number of rounds (Pareto principle) instead of looping.

Maintainer

Gives the goal, approves the plan, answers escalations, does the manual review of the milestone.

Coordinator

The only agent the maintainer talks to. Plans, supervises, guards against chat loops, checks the goal, hands over.

Task manager

Owns the task flow: assigns tasks, runs reviews with a Pareto limit, merges, runs the milestone gate and the retrospective.

Workers (1..n)

Implement one task at a time on their own branch and worktree, run the minimal suite, commit.

Reviewer

Starts one fresh sub-agent per review type on the diff, validates their findings and reports only the confirmed ones. Changes nothing.

Test runner

Runs the minimal or full suite, separates flaky from real failures, bisects regressions to a task, reproduces findings for the reviewer.

The maintainer starts all these agents at the beginning of the run. No agent starts another long-running agent; only the reviewer starts sub-agents, one fresh one per review type and review. OPEN #4

2. How a milestone runs

{{SVG_WORKFLOW}}

The whole flow. Colours: yellow = maintainer, blue = coordinator, purple = task manager, green = worker, red = reviews and tests, grey = git.

Branches

{{SVG_BRANCHES}}

Solid lines: a branch is created from another (the milestone review branch later also gets the milestone branch's merges through $BNG update). Dotted lines: merges after the agents' review. Bold line: the only merge into main, by the watcher after the maintainer's manual review.

  • milestone-<slug> is the only integration branch. The task manager creates it from main, with its own worktree (the milestone checkout), before the first task starts.
  • Every code change reaches it through a task branch: normal tasks, and fix, gap, sync or compensation tasks, also after the hand-off. Before the gate, a sync task merges main in if main has moved.
  • The milestone review task's branch starts from the milestone branch after the gate and targets main. It gets only the milestone review report and, via $BNG update, later merges of the milestone branch. The commits of tasks already merged into the milestone branch count as approved.
  • Nothing merged is ever rewritten; agents never rebase.

4. Setup step by step

  1. Install backlog-ng with milestone branches

    Run the backlog-ng template's bootstrap for the new project and answer yes to milestone branches:

    ./bootstrap.sh --name "<Project>" --project-dir <path/to/project> --milestone-branches yes
# or without flags: question mode asks every setting, incl. run mode, ports and the quality-gate script

    Then start the apps (<backlog-ng>/backlog-ng.sh up) and open the board and the review app. Note the path of the runner: the skills call it $BNG.

    Milestone branches need a backlog-ng version that contains them (still in review in the template). Agent-approved task reviews are not supported yet OPEN #3: until then the task manager merges task branches into the milestone branch itself.

  2. Configure the board

    • Labels: milestone-review (milestone review task), review (drafts from reviews), workflow (improvement tasks from the retrospective).
    • Statuses: To Do, In Progress, In Review, Done.
    • Definition of done per task: task branch, minimal suite green, acceptance criteria covered by tests, agent review recorded in the notes. The manual review item belongs to the milestone review task only.

  3. Provide two test commands

    CommandContentRuns
    minimalFast unit and integration tests; target: a few minutesper task, after every merge into the milestone branch
    fullEverything, incl. end-to-end, container and platform testsonce after the last task, after fixes, before the hand-off

    A common way: one quality-gate script with a flag for the full run, and slow tests marked with a tag so the minimal run can exclude them. The quality-gate script is also what backlog-ng's watcher runs before a merge. OPEN #12

  4. Install the agents and skills

    P=<path/to/project>
mkdir -p "$P/.claude/skills" "$P/.claude/agents"
cp -R skills/milestone-* "$P/.claude/skills/"
cp agents/milestone-*.md "$P/.claude/agents/"

    This installs one agent definition and one skill per agent (see Agents and skills).

  5. Describe the project in CLAUDE.md

    The skills are project-agnostic; everything project-specific comes from the project's CLAUDE.md:

    ## Multi-agent milestone workflow
- BNG: <path to backlog-ng.sh>
- Minimal test command: <command>
- Full test command: <command>
- Docs the reviewers check against: <requirements>, <specs>, <architecture decisions>
- Lessons learned: docs/lessons-learned.md  (created by the task manager with the first lesson)
- Watcher log: <path>  (the task manager's monitor reads it)
- Supported platforms: <list>  (cross-platform review)
- Project conventions: <commit format, code rules, UI spec>

  6. Add the hooks for the hard rules

    Skills are guidance; these rules must be enforced by hooks OPEN #35:

    RuleHook
    No agent merges into, commits on or pushes mainbefore Bash: block git merge/commit/push affecting main
    Package installs only with --ignore-scriptsbefore Bash: block install commands without it
    Web access only to whitelisted domainsbefore web tools and Bash network commands
    Loop guard: the 4th message about one task between the same two agents without a state change is blockedbefore SendMessage: count, block with "escalate to the coordinator"
    Each agent writes only its own files: the coordinator only through $BNG cli, the reviewer only findings files, the test runner only logs and reports, the task manager only diff files, reports, the lessons file and the retrospectivebefore Bash, Edit and Write: block writes outside the agent's allowed paths

  7. Claude Code settings

    • Decide how the agents run: as teammates of one agent team (the coordinator as lead) or as separate sessions with another message channel. The reviewer must be able to start sub-agents. OPEN #4
    • The task manager starts a background monitor in its own session: watcher-log lines and a 10-minute tick (stalled workers) wake it up. OPEN #38
    • Permission mode per agent, model per role, number of parallel workers, token budget. OPEN #31 OPEN #32

  8. Dry run on a demo project

    Before the first real milestone, run a small milestone (2-3 tiny tasks, one deliberate regression) on a demo project and check every path: review rounds, merge queue, full suite, goal check, hand-off, failed merge, retrospective. OPEN #36

How the skills become active

  • Preloaded: listed under skills: in the agent definition. The normal way.
  • User command: only the coordinator's skill is also a slash command (/milestone-coordinator start|status|pause|resume). All other skills are hidden from the maintainer's menu (user-invocable: false).
  • Reference files: the skill says when to read which file, e.g. the reviewer passes each sub-agent only its own type's checklist.

A skill with disable-model-invocation: true cannot be preloaded, so none of these skills uses it. Each description names its agent, so other agents don't pick it up by accident.

Typed, one task per message, no acknowledgements or small talk. Every message must lead to a state change. State lives in the task files; messages are only triggers.

7. Reviews

Scope: only new and changed parts

ReviewDiff
Task reviewgit diff $(git merge-base milestone-<slug> <task-branch>)..<task-branch>
Re-review after fixesonly the fix commits since the previous round
Re-review after the worker merged the milestone branch inthe whole task diff again (logic, code, test)
Milestone reviewgit diff $(git merge-base main milestone-<slug>)..milestone-<slug>
  • Unchanged code is read only for context. A problem in old code counts only if the change makes it reachable or worse; anything else in old code is not reported.
  • Reviewers get the diff as a file and a checkout of the reviewed state for context, and run no git commands: least privilege, and git commands in the maintainer's checkout can lock the repository while the watcher merges.
  • Task branches are never rebased: a red or conflicting merge is aborted before it is committed, and the worker merges the milestone branch into the task branch.

Reviewer and validation

  • For each review the reviewer starts one fresh sub-agent per review type; it has never seen the code and gets only its checklist, the diff, the tree and the lessons.
  • The reviewer validates every finding: format and scope, duplicates across types, and for critical and major findings a re-read in context; where an existing test or a short command can show the defect, the test runner reproduces it. Unconfirmed findings are dropped with a reason and counted.
  • The task manager gets only confirmed findings and applies the Pareto rule. A worker can dispute a confirmed finding; the task manager decides.

To the point

Only findings, each with a concrete failure scenario: no summary, no praise, no general advice, no style preferences. The same defect at several places is one finding. Nothing found: exactly 0 findings.

Pareto rule

RoundScopeBlocks the merge
1task diffcritical, major
2fix diff of round 1critical, major
3fix diff of round 2critical, lesson violations
after 3–critical or lesson violation left: escalate to the coordinator

Minor findings never block; they become drafts without a milestone, which the maintainer sorts at the hand-off. A critical or major finding is never deferred by an agent: at the Pareto limit (or a major left in round 3), and for anything left after the milestone review's single fix round, the task manager escalates "fix or defer" and the maintainer decides. Lesson violations block in every round. OPEN #6

Lessons learned

A basic mistake that caused, or would have caused, a major problem is recorded once in the project's lessons-learned file, so it doesn't happen again. Every review checks the diff against it.

QuestionRule
When is it a lesson?All three: a simple, general cause that a one-line rule could have prevented (unchecked input, path built by string concatenation, missing error path, forgotten platform, test that checks nothing); a critical or major impact; confirmed (by the reviewer, a failed test, or found by the maintainer).
Where do they come from?Confirmed critical/major review findings, full-suite failures and regressions, findings of the maintainer's manual review (always checked: the agents missed them), failed merges into main, workflow incidents.
Who records it, and when?The task manager, right away (not at the retrospective), as a commit lessons: L-<n> <title> on the milestone branch. The maintainer sees every new lesson in the manual review.
How is it used?Workers read the active lessons before they implement. Each review-type sub-agent checks the diff against the active lessons of its review type; the milestone review checks all of them. A violation is reported with lesson: L-<n> and is never minor.
What if it happens again?Text was not enough: the retrospective turns the lesson into a test, lint rule or hook, or sharpens its rule. General lessons are proposed for the reviewer checklists, so other projects benefit too. At most 30 active lessons. OPEN #37
## L-<n>: <short title>

- applies to: <review types, e.g. code, security> | workflow
- severity:   critical | major (what it caused or would have caused)
- seen:       M<n> TASK-<id> (<task review | milestone review | full suite | manual review | merge into main>), ...
- mistake:    one sentence: the basic mistake
- rule:       one sentence, checkable on a diff: what the code must (not) do
- check:      how to spot it in a diff (pattern, search, question to ask)
- status:     active | automated (<test, lint rule or hook>) | retired (<reason>)

8. Guardrails

Hard rules (all agents)

  • Never merge into, commit on or push main; never tick the manual review or set the milestone review task Done.
  • Never rewrite commits already merged into the milestone branch; never touch the maintainer's main checkout.
  • Package installs only with --ignore-scripts; web access only to whitelisted domains.
  • Task files only through the backlog-ng CLI.

Loop guard (coordinator)

  • The 4th message about one task between the same two agents without a state change is blocked, at most 2 rounds on the same question; then the coordinator decides or asks the maintainer. Enforced by a hook.
  • Deadlock check: who waits for whom; cycles and idle agents with assigned work are resolved by the coordinator.
  • Budget per task and milestone; a task over budget is stopped and escalated. OPEN #23

Goal check (coordinator)

  • The maintainer's goal is stored verbatim at planning, with checkable success criteria, and never reworded.
  • Before the hand-off: evidence per goal statement (task, test, demo) or "not met". Missing work becomes gap tasks; an unclear goal becomes a question to the maintainer.

9. Retrospective and improvement

After every merge into main, the task manager writes docs/retros/m<n>.md and compares it with the previous milestones.

MetricPoints to
Findings of the manual review the agents missedreview checklists, review-type selection (most important signal)
Dropped findings per review typevague checklists
Lessons learned seen againautomate the lesson (test, lint rule, hook) or sharpen its rule
Review rounds per task, tasks at the Pareto limittask sizing, acceptance criteria, worker skill
Merge conflicts between parallel tasksdispatch (overlap check), task cut
Regressions found only by the full suitecontent of the minimal suite
Loop-guard events, escalations, stalled workersmessage protocol, missing rules
Time or tokens per taskoverall efficiency
  • Only the 1-3 issues with the biggest effect become an improvement task (label workflow); the maintainer approves every skill change in the review app.
  • A consistency review checks that the skills don't contradict each other and the shared rules stay identical.
  • The next retrospective checks whether each improvement helped; if not, it is reverted.
  • Hard rules, the manual review and the hooks are never changed by an improvement.
