# v1 decisions (Pareto): agreed by all four sessions, waiting for the maintainer

Agreed by the architect, the requirements engineer, the docs reviewer and the critical reviewer (2026-11-14).
Reasons: critical-review.md; the first proposal: pareto-v1-proposal.md. **Not in force until the maintainer accepts
it.** The blueprint files are unchanged.

## Why
Most of the blueprint's complexity (about 25 message types, the loop guard and its hook, `ready`, stall/crash
protocols, one-writer hand-overs) comes from one choice: six long-running peer agents. v1 drops that choice. The goal
is the smallest flow that runs a milestone end to end and can be measured against a simple baseline.

**G0 (new goal; RE):** run the same demo milestone, with the same seeded defects, both v1 and baseline (one session
per task + `/code-review` + the maintainer's review). Maintainer time = logged minutes per interaction. Escaped
defects = seeded defects not caught before the manual review + defects the maintainer finds. Pass = ≥ 30 % less
maintainer time, no more escaped defects and wall-clock time no slower than the baseline; the measured speed-up is
reported, and the maintainer sets a speed target after the dry run. Tokens are reported, not gating; a tie = no go.
The 30 % is the maintainer's starting value, not derived (n = 1). Fair comparison: the baseline runs with the same
parallelism (2 sessions at the same time). The dry run keeps the planned file overlap between 2 tasks and logs
merge-conflict and re-review time separately, so the cost of parallelism is visible.
